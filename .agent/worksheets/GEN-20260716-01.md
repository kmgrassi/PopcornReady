## Goal and acceptance criteria

Fix the production 10-second video path that reaches storyboard generation but
fails while loading keyframe references.

- Reference assets written through the current S3/local object-store layer are
  read back through that same layer.
- Persisted public/private bucket metadata selects the correct physical bucket;
  `DB_BACKEND=supabase` never redirects current asset reads to Supabase Storage.
- Generated-asset and media-analysis temp files preserve a usable extension.
- A missing reference reports a storage/reference failure before the provider
  is invoked.
- Focused unit coverage and a real local storage/database handoff cover the
  production configuration shape.
- Repository validation and independent implementation/wrap-up reviews pass
  before a non-draft PR is opened.

## Production evidence

- Production project: `e1dc9851-deba-47fb-ad6c-a73732f871e9`.
- Production run: `b73d6223-db58-4001-8cc3-9ea2256b2366`.
- Storyboard recovery succeeded and persisted five visible tiles.
- Keyframe job `a41c5e6f-c680-422c-81ba-238a886e2245` then failed with
  `Object not found`; the run projected the terminal error as
  `provider_failed` and never produced clips or an export.

## Research and decisions

- Independent research traced keyframe references through
  `generate-keyframe-job.ts` and `beats.ts` into `generated-assets.ts`.
- Current asset writes use `writeAssetObject()` and `STORAGE_BACKEND`, recording
  `assets-public` or `assets-private` in `storage_bucket`.
- The reference reader instead calls legacy Supabase Storage whenever
  `DB_BACKEND=supabase`. Production therefore looks for an S3 key in Supabase's
  `assets` bucket and fails before the image provider call.
- `asset-analysis.ts` contains the same stale backend selection and is included
  so the shared asset-byte read contract has one implementation.
- Supabase Storage remains restricted to eval fixtures, matching the existing
  public/private storage scope; production asset reads do not add a dual-backend
  fallback.
