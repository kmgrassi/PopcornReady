## Goal and acceptance criteria

Implement "PR 4 — Persistent session and finite-run extension schema" from
`docs/scopes/specialist-agent-orchestration-prs.md`: the one new
`agent_sessions` table, `orchestrator_runs`/`actions`/`jobs`/
`orchestrator_dispatches`/`assets` extensions, the general `action_assets`
relation, and RLS hardening — schema and invariants only (store/lifecycle
logic is PR 5/6). Acceptance: create/reuse one Visuals session, collision-free
concurrent sequence allocation, active-ownership enforcement, immutable
identity, exactly one trusted origin, valid parent/continuation links, one
immutable terminal report action, general action/job/asset attribution, public
denial of raw control data, and cross-project/cross-workspace rejection —
without a synthetic root or duplicate domain tables.

## Decisions

- Two migration files: enum-only `20260716082700` then structural
  `20260716082800` — `ALTER TYPE ... ADD VALUE` cannot be consumed in the same
  transaction and each migration runs in its own transaction under
  `supabase db push`.
- Schema marks use the repo's persisted-JSONB convention (`schema_version`,
  matching `markedJson` and `actions_params_schema_check`), not the TS-side
  `schemaVersion` casing; payload fields (`domain`, `taskKind`) keep the
  contract casing.
- Composite `(id, project_id)` same-project FKs everywhere; the two links that
  overlay existing data (`actions.orchestrator_run_id`,
  `assets.created_by_action_id`) are swapped to composite FKs `NOT VALID` +
  best-effort `VALIDATE` in a `DO` block so a (never expected) legacy
  cross-project row degrades to a loud warning rather than bricking the prod
  deploy; new writes are always enforced.
- `completion_recipient` is a stored generated column derived from
  `origin_kind` so it can never disagree with the trusted origin.
- `allocate_agent_session_sequence` is a single upsert
  (`on conflict ... next_sequence + 1`) — atomic create-or-reuse plus
  allocation; service-role only.
- No `action_assets` backfill in PR 4: between PR 4 and PR 5 only the legacy
  arrays are written, so a one-shot backfill would immediately go stale. The
  four-phase plan (create → PR 5 dual-write + idempotent backfill → assert →
  cutover) is documented in the migration header.
- `origin_actor_id` FK is `on delete cascade` to stay compatible with the
  anonymous-user retention purge.
- Pre-existing hazard (not introduced or changed here): direct
  `orchestrator_runs` deletion trips `actions_guard_immutable` via the FK's
  SET NULL because 20260615 made `actions.orchestrator_run_id` immutable; the
  only real delete path (project cascade) removes actions first, and the new
  composite FK preserves those semantics exactly.

## Review response — Codex P1 (PR #792 comment 3595557298)

Finding: the migration's schema-mark checks required snake_case
`schema_version` while the shared contract (`domain-agent-contract.ts`) marks
DomainTask.v1/DomainReport.v1 with camelCase `schemaVersion`; a verbatim
contract payload would have been rejected by PR 5/6.

Resolution (migration amended in place — verified the file is not on
`origin/main`, so this is not a history rewrite):

- All five new payload checks (task_params, origin_request, pins, session
  summary, domain_report trigger) now validate the contract's `schemaVersion`
  key verbatim; snake_case domain payloads are rejected, not dual-accepted.
- The pre-existing generic `actions_params_schema_check` (marker-presence
  check for ALL action payloads) is recreated to also recognize
  `schemaVersion`, otherwise a verbatim DomainReport.v1 could never satisfy
  it. Strictly more permissive, so revalidation of existing rows is safe;
  legacy payloads keep `schema_version` via `markedJson`.
- The negative probe the reviewer requested exposed a second real hole: a
  payload MISSING the mark key made the CHECK evaluate to SQL NULL, which
  passes. All mark comparisons switched to null-safe `is not distinct from`.
- Integration fixtures are now compile-time `DomainTaskV1`/`DomainReportV1`
  literals imported from `@popcorn/shared/domain-agent-contract`, plus direct
  assertions that a wrong-cased mark is rejected for both the task and the
  report.
- Re-validated end to end: `supabase db reset --local` replay, 21-probe SQL
  smoke, 17/17 supabase TS tests with `RUN_LOCAL_DB_INTEGRATION=1`,
  `pnpm agent:lint:fix`, `pnpm agent:validate -- --scope api` — all pass.
