## Decisions

- Catalog only the current primitive vocabulary. Future domain dispatch and
  standalone generic generation tools join the catalog in their owning PRs.
- Keep `createDefaultToolRegistry()` as the flat production source. Explicit
  role builders filter the same definitions but are not wired into production.
- Make the rich primitive `ToolDefinition` require metadata derived from the
  catalog, while keeping driver test doubles compatible.
- Treat `request_approval` as a root-owned approval capability; domain
  registries cannot contain it.
- Keep same-domain recovery tool calls available. Cross-owner recovery tool
  names are removed from the domain-safe projection and replaced with the
  required owner/domain plus exact project-scoped targets from a server-trusted
  target set. Bounded hint identifiers can select only those authorized targets;
  they cannot authorize a target. Unknown historical tool strings fail closed,
  raw errors remain unchanged, and the projection is not wired into the flat
  model, engine, persistence, or audit.
- Preserve the current API projection behavior exactly. Known labels come from
  catalog projection metadata, while `regenerate_image_asset` deliberately
  retains its current stage-label and fallback-order behavior.
- Preserve the exact driver-stub descriptions separately from short run labels.
  Driver stubs, rich handlers, and the bridge all receive catalog metadata;
  cost classes remain classifications rather than executable cost behavior.
- Classify `regenerate_image_asset` as synchronous media work. Its active rich
  handler/bridge was already synchronous; the old dormant stub's media-name
  set incorrectly made it async, so exact legacy stub-mode parity is neither
  claimed nor desired.
- Treat `request_approval` as the only approval execution/gate invariant. The
  catalog is pure apart from the shared `AgentRole` type and owns all metadata.

## Changes

- Added the frozen, ordered current-primitive catalog at
  `apps/api/src/lib/orchestrator-tools/capability-catalog.ts`. It is now the
  only `ToolName` definition and owns owner role, capability, canonical label
  and order, exact driver description, execution, cost class, approval gate,
  and legacy run-projection compatibility metadata.
- Required catalog metadata on rich and driver `ToolDefinition` shapes. Every
  current rich primitive uses the catalog helper, rich registration rejects
  metadata drift, driver overrides reject drift, and the production bridge
  carries metadata without changing model descriptions or schemas.
- Preserved the active `createDefaultToolRegistry()` definitions and insertion
  order. Added dormant explicit root, Visuals, and Audio builders over those
  same definitions; their exact disjoint ownership counts are 10/6/2.
- Canonicalized the previously duplicated tool unions in orchestrator types,
  rich-tool types, tool errors, and legacy invocation persistence while
  retaining the broader `database_error` classification semantics.
- Added a pure, dormant recovery projector. It uses a trusted nonempty project
  ID plus an exact server-authorized `DomainTarget` set, preserves same-owner
  actions, redacts both cross-owner recovery fields, removes raw hints, merges
  duplicates, fails closed on unknown names/IDs, validates stable-ID shape and
  length, caps targets, and never mutates raw audit data.
- Derived existing API run labels/order from explicit catalog projection
  compatibility data. `regenerate_image_asset` intentionally retains the
  existing `Plan` / fallback-order result instead of silently changing UI.
- Updated the domain contract, roadmap status, repository map, and tool-test
  harness documentation.
