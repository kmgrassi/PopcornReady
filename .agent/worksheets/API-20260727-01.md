## Decisions

- One additive migration (`20260727120000_session_claim_and_job_fencing.sql`)
  because atomic claim/release increments and the finalization fence need SQL
  (PostgREST cannot express `claim_generation = claim_generation + 1` or the
  job→action→run→session comparison in one statement). Everything else reuses
  the PR 4 schema unchanged.
- The fence is a `jobs` BEFORE UPDATE trigger on terminal transitions
  (`succeeded`/`failed`), so every finalization path — including #805's
  `complete_provider_job_execution` — is fenced without modifying that
  function. `canceled` stays unfenced so the new claim owner can clean up
  stale jobs. `jobs.session_claim_generation` is immutable once set.
- `claim_agent_session_run` claims a specific run (idempotent re-claim keeps
  the generation; a foreign active run returns `held`). Selecting the
  earliest eligible sequence and dispatch-lease composition is PR 6 scope.
- The domain-session store lives in the scope-mandated new module
  `domain-session-store.ts`; no `index.ts` aggregator.
- The duplicate-report violation maps to the existing `idempotency_conflict`
  ApiError code (409) with `reason: "domain_report_exists"` rather than a new
  error-code union entry; replaying the same report action id returns the
  existing action.
- `completeDomainRun` derives the recipient exclusively from the DB-generated
  `completion_recipient` column and only invokes the injected `wakeParent`
  when this caller wins the terminal transition of a `creative_director`
  origin run — creator-direct completion structurally cannot wake anything.
- Job launches stamp `session_claim_generation` by reading the launching
  run's session claim (generation only advances when ownership changes, so
  the current value while owning equals the claim-time value).

## Review response (PR #813 Codex findings)

- **P1 — active ownership before copying the claim generation**
  (`domain-session-store.ts` `getRunSessionClaim`): the lookup now returns a
  claim only when `agent_sessions.active_run_id === runId`; queued or stale
  sibling runs (and ex-owners after release) get `null`, so their jobs are
  never stamped with the active owner's valid generation and cannot slip past
  the finalization fence. Tests: queued sibling on the same session obtains
  no claim; ex-owner after release obtains no claim.
- **P2 — report replays must not write drifted outputs**
  (`appendDomainReport`): a same-id replay is validated against the persisted
  immutable params with a canonical deep-equal; a drifted payload is rejected
  with typed `idempotency_conflict` (`reason: domain_report_replay_mismatch`)
  and writes nothing. Attribution is only ever derived from the PERSISTED
  report (which also heals a crash between the action insert and its
  attribution write). Tests: identical replay is a no-op returning persisted
  state; drifted replay is rejected and `action_assets` rows are unchanged.
- **P2 — terminal status checked before owner re-claim**
  (`claim_agent_session_run`): the terminal-status branch now precedes the
  owner re-claim branch, so a run that became terminal while still recorded
  as `active_run_id` (crash between completeDomainRun's terminal update and
  the separate release) returns `terminal` instead of `claimed`; release
  remains the separate cleanup operation. The migration was amended in place
  (verified absent from `origin/main`, never applied anywhere). Tests: crash
  window claim returns `terminal`; release still succeeds; static ordering
  assertion in the migration test.
- Merge: `origin/main` (#809–#811 typing refactors) merged into the branch;
  the only conflict was the append-only feedback log (both entries kept); no
  code conflicts, typecheck/build re-verified.
