## Goal and acceptance criteria

Create an implementation-ready scope for agent-operated browser testing against
the deployed Netlify, Railway, Supabase, S3/CloudFront, and provider paths.

Acceptance requires:

- an explicit definition of safe production coverage and excluded irreversible
  behavior;
- a phased PR plan with dependencies, tests, rollback boundaries, and done
  criteria;
- release-coherence, authentication, tenancy, cleanup, cost, concurrency, and
  evidence requirements;
- an executable-agent flow contract and production coverage matrix;
- repair of active manual-testing documentation that directly conflicts with
  the current route table or tested behavior;
- independent research, plan, implementation, and wrap-up review;
- `pnpm agent:lint:fix` and
  `pnpm agent:validate -- --scope docs`.

## Decisions

- Keep fast deterministic local Playwright and local-Supabase integration
  coverage; production coverage adds a distinct tier rather than replacing it.
- Define "test everything in production" as exercising deployed production
  binaries and services against isolated test identities and workspaces, never
  customer data.
- Require one release identity across the deployed web, API, and database
  readiness contract before a production browser run starts.
- Add a separate remote Playwright configuration that starts no local servers
  and fails closed on an unexpected host or release.
- Do not enable or repurpose the existing dev-only sandbox router in
  production. Use a separately threat-modeled, service-authenticated control
  plane.
- Provision explicit QA membership with `public.users.id`; browser operations
  use the normal request-scoped Supabase path so RLS remains under test.
- Use typed direct-Postgres transaction modules for new trusted multi-table
  control-plane workflows. Do not add new application workflow RPC targets.
- Treat database deletion as only one part of cleanup. Jobs, storage, provider
  artifacts, notifications, analytics, webhooks, credits, and late workers
  require explicit handling.
- Keep real provider work opt-in and budgeted. Keep irreversible charges,
  destructive account/admin behavior, and fault injection out of production.
- Store living coverage separately from immutable per-release evidence.

## Blockers and risks

- Production mutation work must not begin until the release identity and
  control-plane threat model are implemented and reviewed.
- Public-sharing behavior is intentionally unavailable to `internal_test`
  workspaces under current visibility policies; the scope must select a safe
  canary design before automating that flow.
- Current authentication resolves one owned workspace per domain user.
  Mutating production tests therefore require one ephemeral auth/domain identity
  per sandbox unless a separate product-level workspace selector is implemented.
