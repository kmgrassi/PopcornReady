## Goal and acceptance criteria

Fix the production board-revision no-op: an image tile revision must create a new immutable image asset/version, and a targeted revision must not be reported as succeeded before a downstream action is applied.

## Decisions

- Treat image tile feedback as an image regeneration request and use the existing immutable asset-version service.
- Keep other feedback scopes on the orchestrator because their required rerun inputs differ by media kind.
- Guard targeted feedback so a model `done` response cannot convert a no-op into success.

## Changes

- Terminal image-tile revisions now call the immutable image regeneration service directly, attach its provenance action to the originating run, and project it into asset-generation progress.
- Direct run revisions perform the same platform-key credit precheck and debit accounting as orchestrator generation; provider-key users remain unbilled.
- Targeted tile/asset feedback can no longer finish as a no-op: completion requires a later output-producing revision action, otherwise the run fails with `revision_not_applied`.
- Target assets are validated before the feedback action is persisted.

## Independent reviews

- Research/plan: independent reviewer recommended that revision completion be evaluated only against actions after the latest feedback, and warned against unbounded model retry loops. Implementation will incorporate this guidance.
- Implementation: independent reviewer identified missing output filtering, direct-path credit accounting, synchronous response semantics, and target-validation ordering. All P1 items were resolved; the reviewer confirmed no remaining P1 in the successful direct image path.
- Wrap-up: validation evidence and documentation reviewed; no unresolved release blocker.

## Blockers and risks

- The generic revision surface also supports non-image targets; do not route those to the image-only service.
- Existing unrelated untracked files must remain untouched.
- The direct image path is intentionally limited to terminal runs to avoid racing a live orchestrator; active-run revisions retain the model-mediated flow but cannot silently report success.
