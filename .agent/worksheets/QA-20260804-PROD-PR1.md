## Goal and acceptance criteria

Implement PR 1 from `docs/scopes/production-browser-agent-testing.md` so a
read-only verifier can prove which compatible web, API, and database release it
is about to test. This PR must not add production login automation, sandbox
mutation authority, provider spend, or browser-held trusted credentials.

## Decisions

- Use the immutable commit SHA as the shared release orchestration ID.
- Give each deploy surface a distinct SHA-256 artifact hash; never treat the
  shared commit as proof that Netlify and Railway built the same artifact.
- Define database compatibility as the deployed ledger containing the API
  build's exact canonical migration-version set. Extra applied versions may
  appear anywhere because the repository intentionally supports out-of-order
  additive migrations with `--include-all`.
- Keep `/api/v1/health` backward compatible by retaining `commit` while adding
  structured release and migration fields.
- Render the existing route hierarchy from a typed registry without changing
  layouts, access guards, redirects, page components, copy, or styles.
- Keep production evidence dated and immutable; keep the route registry and E2E
  inventory as living coverage truth.

## Blockers and risks

- Production mutation remains blocked until PRs 3-7 of the production-browser
  plan land. This PR must not weaken that boundary.
- Netlify and Railway expose different provider-specific commit variables; the
  manifest generator must normalize them into one explicit contract.
- Migration history can contain extra lower or higher versions during a
  compatible rollback; first-N prefix or total-length equality would incorrectly
  reject the repository's supported out-of-order additive migration policy.
