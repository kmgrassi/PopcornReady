## Goal and acceptance criteria

Replace the protected creator-direct confirmation route's
`consume_creator_direct_proposal_gate` Supabase RPC call with a typed
`withTransaction` module without changing the route contract or weakening its
authorization, cost, replay, or concurrency guarantees.

- The API transaction owns the gate/run/idempotency orchestration.
- `reserve_orchestrator_run_budget` and `wake_orchestrator_dispatch` remain
  reviewed database-native integrity/concurrency primitives invoked on the same
  transaction client.
- A migration grants `popcorn_api` only the required table columns and routine
  execution.
- Unit and local Postgres integration tests cover observable state and rollback.
- The RPC boundary allowlist and authoritative documentation are updated.
- The production API path is smoke-tested after the PR is ready; the legacy
  function is retained until the new caller has been deployed and observed.

## Research

- Route operation `agentCreations.confirmProposal` currently invokes
  `public.consume_creator_direct_proposal_gate`.
- The latest function definition is in
  `20260729170000_creator_direct_pgcrypto_schema.sql`.
- It locks and validates `orchestrator_run_gates`, locks the scoped
  `idempotency` record, validates replay hashes, locks the matching queued
  creator-direct `orchestrator_runs` row, reserves a run ceiling, consumes the
  gate, wakes dispatch, and records the response.
- The role `popcorn_api` is provisioned in production with connection/schema
  usage but no table or routine grants.
- The production Supavisor session-pooler URL requires
  `sslmode=require&uselibpqcompat=true` for the current Node `pg` driver.
- `popcorn_api` is intentionally `NOBYPASSRLS`; column grants alone cannot see
  the RLS-protected tables. The migration therefore needs role-specific
  policies as well as column grants.
- The transaction must accept `workspaceId` and prove
  `projects.workspace_id` matches before treating the gate as authorized.
- Applying grants and deploying the caller are independent post-merge jobs.
  The grant migration must be applied and verified before the Railway caller is
  allowed to take traffic.

## Decisions

- Keep budget admission and dispatch wake as database-native routines: both
  encapsulate reusable locking/integrity behavior shared by other workflows.
- Keep `popcorn_api` as `NOBYPASSRLS`. Add role-specific policies only on the
  four tables this transaction reads or writes, backed by column grants.
- Do not lock the immutable idempotency row: the locked gate serializes same-gate
  confirmation, while the idempotency primary key fences cross-gate reuse.
- Retain the explicit outer queued-run lock before budget admission. The budget
  routine then performs its own root/run locking and budget revalidation.
- Do not drop `consume_creator_direct_proposal_gate` in this PR. Remove it only
  after the new production caller is deployed and observed.
- Preserve the current public error envelope by mapping direct Postgres failures
  to the stable `agentCreations.confirmProposal` database operation.
- Before merging the caller, apply and verify the additive grants migration in
  production; retaining the legacy function keeps that staging step harmless.

## Blockers and risks

- Direct Postgres does not carry request JWT identity; role-specific policies
  permit only the explicitly granted columns, while every query must remain
  workspace/project/actor scoped.
- Grants must be sufficient for the existing SQL primitives without granting
  broad table access or ownership.
- Numeric digest construction must match PostgreSQL `double precision::text`
  behavior for existing idempotency rows.
- Supabase migrations and Railway deploy independently. Production readiness
  returns 503 until the grant/policy migration is visible so Railway retains
  the prior healthy deployment.
