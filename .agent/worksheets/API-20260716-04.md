## Goal and acceptance criteria

Implement PR 5, “Idempotent action lifecycle, session store, and provenance
wiring,” from `docs/scopes/specialist-agent-orchestration-prs.md`. The completed
slice must preallocate the action/tool-call identity before mutating tool work,
make retries reuse it, atomically reserve API idempotency, fence provider job
launches, and retain action-to-job-to-asset provenance. The PR-level acceptance
is the scope's concurrent crash/retry proof: one logical invocation produces one
action and provider launch, with traceable trusted origin lineage.

## Decisions

- Begin at the engine durability boundary: persist a caller-supplied UUID action
  in `running` state before a tool handler can perform external work, then patch
  that same row to its terminal or accepted state.
- Keep a per-call `toolCallId` distinct from `actionId`: only an engine-reserved
  `actionId` may be written to `jobs.action_id` or used as a job idempotency key.
- Keep the PR 4 schema migration immutable; add follow-up migrations rather than
  rewriting merged history.

## Changes

- `orchestrator/engine.ts`, `tool-context.ts`, and `retry.ts`: reserve an
  action UUID in `running` state before executing a mutating tool; use it as the
  canonical tool-call id; patch the same action with job/output/error state; and
  safely retry its persistence operation.
- `api/v1/store.ts` and `store-types.ts`: support a caller-reserved action id
  with insert-first/reload-on-conflict semantics, preserving immutable action
  audit fields.
- `packages/shared/src/v1/types.ts`, `store-composition-jobs.ts`, and
  `job-gateway.ts`: map `jobs.action_id` through the shared job contract and
  persistence layer.
- Async storyboard, anchor, keyframe, clip, audio, and export tools: use the
  engine-reserved action id as their tenant-scoped job idempotency key, persist
  it on the job, and launch a local worker only for a newly-created job. Direct
  tool/test calls with only a correlation ID do not claim an action row.
- Focused engine and retry tests cover pre-execution action persistence,
  canonical context identity, and retry behavior.
- PR review follow-up: finalise a reserved action when cost estimation, balance
  lookup, or provider-key lookup fails before a tool handler starts.

## Independent reviews

- Research/plan review completed: start with a narrow durable
  invocation-to-job-provenance slice; do not mix PR 6 dispatch/wake semantics.
- Implementation review completed. The current slice is a useful foundation,
  but it found three PR-blocking gaps before handoff: the canonical action is
  not yet consumed by generated-asset workers, HTTP idempotency is still
  process-local find-then-save, and provider launch lacks a queued-to-running
  compare-and-set claim. It also found that a process restart cannot yet
  reconcile a preallocated action with no recorded job before asking the model
  for another decision.
- Wrap-up review confirmed the above P0 gaps and found one omitted async
  primitive: `edit_video_asset` has not yet received canonical action/job
  provenance. The PR description must explicitly mark this branch as
  in-progress and not ready to merge.
- PR review follow-up completed: the engine passes a durable `actionId` only
  after reservation, async tools use that field rather than arbitrary
  `toolCallId` values, and preflight failures now finalise the reserved action.
  Independent review found no correctness blockers and requested the direct
  tool-context regression test, which is included.

## Blockers and risks

- The current API idempotency helper is an in-process mutex plus find-then-save,
  so it is not safe across API instances. This requires a service-only Postgres
  reservation/consume RPC rather than a client-side retry wrapper.
- Async tools currently create provider jobs after the engine invokes them; PR 5
  now carries the preallocated action and idempotency key. The next slice must
  add the database compare-and-set provider claim and use that same action when
  generated assets are persisted.
- Do not claim PR readiness from the current branch: the independent
  implementation review identified the cross-instance idempotency reservation,
  provider claim fence, crash-window reconciliation, and action-to-asset
  provenance as required remaining work.
