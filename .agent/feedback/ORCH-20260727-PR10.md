## Lesson

Stable-target helpers are not a safety boundary until the engine invokes them
before the first durable or provider side effect. A parse-once preparation seam
keeps model validation, trusted scope, action params, cost estimation, and tool
execution from drifting.

A finite-run session claim fences provider work, but it does not authorize a
late active-selection write. Claimed domain media should stay pooled unless an
explicit transactional selection operation owns compare-and-swap semantics.
In-session prerequisite recovery can safely rejoin pooled outputs through
immutable creation-action attribution to the exact run plus stable beat or
anchor identity.

Relational story IDs and plan IDs are separate namespaces even when fixtures
make them look alike. Carry relational storyboard/scene/beat identities until
the active plan is loaded, then translate through the exact storyboard's
positional mapping. A scoped storyboard revision must merge over validated
untargeted panels and publish a complete new attempt. Because tile assets,
relational rows, and the project pointer are all visible graph state, a session
claim check in application code is insufficient: claimed publication needs one
idempotent transaction that revalidates the job/action/run claim and every
plan, pointer, and preservation CAS token.

For scoped filters, `undefined` means unscoped while `[]` means the trusted
target resolved to no beats. Conflating those states widens a zero-beat scene
target to the full plan. Beat-producing tools must preserve the distinction and
fail closed, and domain storyboard entry must reject a missing run/claim/action
before creating a durable job.

An atomic commit is not durable replay by itself. Preallocate every bundle ID
from the durable job identity, persist an immutable payload fingerprint and
result, and check replay before active-state rejection. Recovery must look for
that deterministic bundle before regenerating or uploading provider output, or
it can overwrite committed bytes after a lost response. The database must also
derive the complete expected beat manifest from the selected plan and validate
every submitted panel/asset mapping before the transaction's first insert;
validating only the caller's preservation list leaves omissions and swaps
unfenced.

Flattening only beats is also insufficient because valid plans may contain
zero-beat scenes. Validate the exact scene manifest separately, and do not
accept caller-computed graph fingerprints without recomputing their canonical
form from an exact edge/params payload. If visibility and terminal job status
can diverge, crash recovery can report a published success as failure; commit
the immutable bundle, current pointer, persisted result, and job success
together, with a provider-free deterministic recovery probe as defense in
depth.
