## Lessons

Column grants do not make a direct role useful when RLS still denies every row.
The narrowest workable boundary is a `NOBYPASSRLS` role with both column ACLs
and role-specific policies for the reviewed row family.

`SELECT ... FOR UPDATE` also requires UPDATE privilege. Granting only
`UPDATE(updated_at)` and a creator-direct-only policy preserves the queued-run
lock without authorizing status or ownership changes.

Migration and application deployment are separate production races. A health
check that verifies the required database capabilities allows Railway to keep
the previous deployment live until the additive migration exists. Hosted
detection must not depend only on `NODE_ENV`, because Railway can omit it.

`NOBYPASSRLS` alone does not prove an RLS-bound role: superusers and table
owners bypass RLS too. Readiness must reject all three bypass paths.
Required positive grants are also insufficient for a least-privilege rollout:
health must reject inherited memberships, unsafe role attributes, broad table
grants, and column privileges outside the reviewed transaction.

The legacy idempotency digest includes PostgreSQL's
`double precision::text`. Returning that canonical representation from the
locked gate query avoids subtle JS exponent-format incompatibilities.

Local Supabase global roles belong in `supabase/roles.sql`; a role created only
inside a database migration can disappear when `supabase db reset` rebuilds the
database/container boundary.
