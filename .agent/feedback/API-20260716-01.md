## Lesson

A comparison eval is only trustworthy when exactly one variable differs
between the compared architectures. Reusing the production system prompt,
routing context, and registry-composed tool descriptions for the fixture
hierarchy surface — while making the fixture tools structurally
non-executable (no `execute`, definitions only) — keeps the comparison about
the tool surface and makes "never duplicate live billable generation" a type-level
property rather than a discipline. Classifying each sampled decision into a
failure taxonomy (wrong tool / premature done / unnecessary turn / repeated
failed call) turned the gate from a pass rate into dimensions the adoption
record can actually reason about, and deriving `repeated_failed_call` from the
scenario's own last failed result avoided a second annotation channel that
could drift.

## Follow-up

The `--fixture` offline mode proved the report plumbing without spending
tokens; consider the same pattern for other key-gated report scripts. The
acceptable sets of the new families should be calibrated after the first real
baseline run, per the harness's original follow-up note.
